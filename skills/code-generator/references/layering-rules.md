# 分层与模块化规则（代码生成的骨架与护栏）

这份文档定义本 skill 生成代码所遵循的**分层模型、依赖规则、可注入接口、同层解耦、目录与命名**。
目标是让生成的代码天然具备三大质量属性：**可移植**（硬件相关被抽象层挡住）、**可维护**（高内聚低耦合）、
**可测试**（接口清晰、实现可替换/可打桩注入）。

> 重要：下面是本 skill 的默认架构基线。SAD 若未描述或与其一致，就采用该基线；SAD 若明确指定不同架构，
> 必须先向用户展示差异，由用户决定采用 SAD 还是 skill 默认架构。用户未决策前不得生成配置、架构图或代码。

## 1. 分层模型（说明用的典型层序，高 → 低）

| 序 | 层 | 职责 | 典型内容 |
|----|----|------|----------|
| 1 | **App 应用层** | 业务逻辑、功能编排、状态机；向 Service 下发命令/目标值，不直接访问 HAL | 各业务模块（一个功能一个模块）、主编排/任务调度 |
| — | **Bus 横切层**（可选） | 同层模块间解耦的数据/事件通道 | 信号总线（状态数据池）、事件总线（发布/订阅） |
| 2 | **Service 服务层** | 与硬件无关的通用服务、硬件能力门面、资源仲裁与实时算法 | **Native/Device Service**（对 App 暴露设备能力并受控调用 HAL）、诊断、参数/NVM、协议栈适配、OSIF、**控制/信号处理算法核**（FOC、PID、滤波、状态估计等） |
| 3 | **HAL 硬件抽象层** | 把"做什么"与"用哪块硬件做"解耦；按设备类型选择直连 MCAL 或经 CDD 访问 | 每类外设一个抽象接口（GPIO/ADC/PWM/CAN/定时器/看门狗…）：接口 `.h` + 实现 `.c` |
| 4A（平级） | **CDD 复杂驱动层**（可选分支） | 总线外挂芯片的专用驱动，不是 HAL 与 MCAL 之间的必经层 | 电源管理 IC、BMS 前端、外部传感器/存储器等驱动（前缀 `CDD_`） |
| 4B（平级） | **BSW 基础软件栈**（可选分支） | 与 CDD 同层并列的第二条驱动栈：AUTOSAR 通信/诊断/存储/模式基础软件，经 MCAL 的总线/存储驱动落到硬件 | CanIf/Com/PduR、Dcm/Dem/Det、NvM/MemIf/Fee、CanSM/ComM 等（多为 AUTOSAR 原名，无统一前缀） |
| 5A（平级） | **MCAL 微控制器抽象层** | 片上外设寄存器级驱动，同时为 CDD/BSW 提供 SPI/I2C/CAN 等总线能力；直接运行在硬件上 | 芯片厂/AUTOSAR MCAL（Adc/Dio/Icu/Wdg/Spi/I2c/Can 等，多为 SDK 自带，不重造） |
| 5B（平级） | **OS / RTOS** | 调度、任务、同步原语；与 MCAL 平级且直接运行在处理器内核/硬件上 | FreeRTOS/AUTOSAR OS、任务/队列/信号量、板级启动 |

- **HAL/CDD/BSW/MCAL 默认采用分叉拓扑，而不是一条强制串行链。CDD 与 BSW 是同层并列的两条可选驱动栈：**

  ```text
          ┌──────────────────────┐
          │         HAL          │
          └─┬──────────┬──────┬──┘
     片内    │  外挂芯片 │      │  通信/诊断/存储/模式
            │     ┌────▼─┐  ┌─▼────┐
            │     │ CDD  │  │ BSW  │   （平级 · 互不依赖）
            │     └────┬─┘  └─┬────┘
          ┌─▼──────────▼──────▼──┐
          │         MCAL         │   (Adc/Dio/Icu/Wdg + Spi/I2c/Can)
          └──────────────────────┘
  ```

  - **片内外设路径：`HAL → MCAL`。** 例如 HAL 的 ADC/GPIO/PWM/Timer/Watchdog 实现直接调用相应 MCAL。
  - **外挂芯片路径：`HAL → CDD → MCAL`。** HAL 暴露设备能力；CDD 实现 PMIC/BMS AFE/外部传感器等芯片协议；
    CDD 再调用 MCAL 的 SPI/I2C/CAN 等总线驱动。
  - **基础软件路径：`HAL → BSW → MCAL`。** BSW 实现 AUTOSAR 通信/诊断/存储/模式基础软件（CanIf/Com/PduR、
    Dcm/Dem/Det、NvM/MemIf/Fee、CanSM/ComM 等），再调用 MCAL 的 Can/Spi/Fls 等总线/存储驱动落到硬件。
  - CDD 与 BSW 都是**可选分支**，并且**彼此平级、互不依赖**（声明在同一 `peer_groups`）。HAL 不得绕过 MCAL
    直接操作寄存器，CDD/BSW 也不得直接操作寄存器。
  - 在 `layers.json` 中用 `architecture_edges` 声明 SAD 的合法结构边。采用本默认模型时至少声明
    `["Hal","Mcal"]`、`["Hal","Cdd"]`、`["Hal","Bsw"]`、`["Cdd","Mcal"]`、`["Bsw","Mcal"]`，并用
    `peer_groups` 声明 `["Cdd","Bsw"]`；这类结构边不是架构偏离，不放进 `allow_edges`。
- **MCAL 与 OS/RTOS 属于同一个基础软件平台级，但彼此是独立层：**

  ```text
           Service / OSIF                 HAL / CDD
                 │                           │
          ┌──────▼──────┐             ┌──────▼──────┐
          │  OS / RTOS  │             │    MCAL     │
          │ 调度 / 同步  │             │ 片上外设驱动 │
          └──────┬──────┘             └──────┬──────┘
                 └──────────┬────────────────┘
                            ▼
                 MCU 内核 + 片上/板级硬件
  ```

  - 二者都直接建立在处理器内核、异常/中断机制和片上硬件之上，不把对方当作下层。
  - 默认**禁止 `MCAL → OS` 和 `OS → MCAL`**；MCAL 驱动不使用任务、队列、互斥量等 OS 服务，OS 内核也不依赖
    项目的 MCAL 外设接口。需要调度/同步能力的驱动适配应放在 HAL/Service 或单独的适配模块。
  - Service 中的 OSIF 可通过结构边 `Service → Os` 使用 OS 原语；HAL/CDD 通过各自结构边使用 MCAL。
  - 在 `layers.json.peer_groups` 中声明 `["Mcal","Os"]`。平级只表示**架构高度相同**，不表示允许互相 include；
    若某项目确有依赖，必须由 SAD 明确给出 `architecture_edges`，不能因“平级”自动放行。
- **横切层（cross-cutting）**：像 `Types`（公共类型/返回码）、`Bus`（信号/事件总线）、`Cfg`（全局配置）这类，
  **任何层都可依赖**，不参与"跨层"判定。它们必须**零业务逻辑、零硬件依赖**，否则就破坏了分层。
- 实际项目可能合并/增删层（如无 CDD、或 App 直接在 RTOS 上）。这类 SAD 差异先触发用户决策门；用户选择 SAD 后
  才在 `layers.json` 中如实声明，选择 skill 默认架构则按默认基线生成并记录对 SAD 架构项的覆盖。
- **标准控制路径是 `App → Native/Device Service → HAL`。** App 只调用 Service 的业务/设备能力接口，下发命令、
  目标值、启停请求并读取状态；Native/Device Service 负责权限/参数校验、资源仲裁、生命周期、并发和错误处理，再调用
  HAL 的 `IF_*` 接口。这里的 "Service" 表示架构角色：在 MCU 单进程工程里通常是普通 C 模块和直接函数调用，
  不要求实现成独立进程、IPC 或消息队列，因此可以保持很低的调用开销。
- **Service 对 OS/RTOS 的依赖只由 OSIF 承担。** Native/Device Service 面向 HAL，OSIF 面向 OS/RTOS；架构图和
  模块依赖应分别表达为 `Native/Device Service → HAL` 与 `OSIF → OS/RTOS`，不能用一条从 Service 整层发出的箭头
  混淆两类职责。OSIF 只封装任务、同步、队列、时基等 OS 能力，不参与硬件设备访问。
- **算法实现放 Service 层，不放 App、不放 HAL/MCAL。** 把算法拆两半：**①算法核**（控制律/变换/调节器/滤波等纯数学，
  **零硬件依赖、零业务编排**）放 **Service 层**做成独立模块 → 可主机单测、可移植；**②I/O 接驳**（取采样值、写执行量）
  一律经 **HAL 接口**（`IF_Adc/IF_Pwm/IF_Timer…`）。App 只下设定值/启停、收状态，不实现算法；算法核也不直碰寄存器。
  **实时路径在 Service 内部闭环执行**：周期任务/定时器触发 → 读 HAL 采样 → 运行算法核 → 写 HAL 执行量，而不是让 App
  高频穿过 Service 逐次驱动 HAL。
  *为什么*：算法核混进 App 会把硬实时时序钉死在业务上、换电机/换芯片要动业务码且无法单测业务；沉进 HAL/MCAL 则
  破坏"无状态硬件抽象"、纯数学也不再可移植可主机测。*例外*：硬实时环路（如 10~20kHz 电流环）若受不了 HAL 间接调用，
  可让该算法模块直调 MCAL——但须在 `layers.json` 的 `allow_edges` 里显式登记并注释，绝不默默跳层（见 §2、§4.5）。
- **存在独立 Service 层时，App 默认禁止直接访问 HAL。** 若裁剪型小项目明确合并了 App/Service，或有量化性能数据证明
  标准路径不满足要求，才可由 SAD 明确批准例外，并在 `layers.json.allow_edges` 登记依赖、理由和适用模块；即使放行，
  也只能访问 HAL 的公开 `If/`，不得访问 `Impl/`、CDD 或 MCAL。

## 2. 依赖规则（check_layering.py 据此判定，违规即门禁失败）

把"上层可访问下层，不能跨层"落成可机检的三条规则：

1. **只能沿架构边向下，平级默认隔离。** 任一模块不得 `#include` 比自己**更高层**的头文件。位于同一
   `peer_groups` 的不同层也不得互相 include，除非 SAD 明确声明结构边。下层永远不知道上层存在——
   这是可移植与可测试的根。HAL 不认识 App；MCAL 不认识 HAL。
   *为什么*：一旦下层反向依赖上层，换硬件/换业务/单独测一层都得拖着整棵树，分层就名存实亡。

2. **沿架构边向下，不准任意跳层。** 上层只依赖**相邻的下一层或 `architecture_edges` 明确声明的结构边**
   （+ 同层 + 横切层），不得沿 SAD 未定义的路径直够更底层。CDD/BSW 都是可选分支，因此 `HAL → MCAL` 虽跨过图中的
   CDD/BSW 行，仍是默认合法结构边；它不属于架构偏离。
   App 要使用硬件能力，应调用 Service 的 Native/Device Service 公开接口，由 Service 再调用 HAL；App 不直接
   `#include` HAL、CDD 或 MCAL 头文件。需要更底层能力时，让相邻下层**封装一个接口**暴露上来。
   *为什么*：跳层会把"中间层换实现就能移植/打桩"的能力打穿——App 里散落的 MCAL 直调，会让换芯片变成全工程
   大改、让单测 App 时必须拉起真实寄存器。
   *放宽*：少数项目允许 App 直接用 OS 原语。若确属架构决策，在 `layers.json` 的 `allow_edges` 里**显式登记**
   这条例外（带注释说明），而不是默默放任。能不开就不开。

3. **同层之间不得硬耦合，平级层之间默认零依赖。** 同一层内的模块**不应**互相 `#include` 对方私有头、不应直接
   调对方内部函数；`peer_groups` 中的不同层（默认 MCAL 与 OS）则连公开接口依赖也不自动允许。要协作，走
   **横切总线**（信号/事件）或对方的**公开接口契约**。
   *为什么*：A 直接调 B 内部，A 就钉死在 B 上，B 一改 A 就崩，也没法单独给 A 打桩。总线/公开接口让同层模块
   各自独立编译、独立测试、独立替换。

> check_layering.py 只能看 `#include` 边（这是 C 里依赖的物理体现）。同层"只经公开接口"这种语义约束，
> 部分靠规则 3 的 include 检查兜底，部分要靠代码评审 + conformance 清单人工确认。

## 3. 可注入接口：HAL 的 If / Impl 拆分（可移植 + 可测试的关键）

硬件抽象层的每类外设拆成**接口**与**实现**两半，这是让硬件相关代码"可替换、可打桩注入"的核心手法：

```
HAL/
├── If/                      # 接口（与硬件无关，上层只认这里）
│   ├── IF_Gpio.h            # 公开函数原型 + API 契约（线程安全/ISR 安全/阻塞/返回码）
│   ├── IF_Gpio_Cfg.h        # 编译期配置（通道枚举、引脚映射占位）
│   └── IF_Adc.h ...
└── Impl/                    # 实现（对接具体 MCAL/CDD/SDK）
    ├── IF_Gpio.c            # 调 MCAL/CDD 把接口落到真实硬件
    └── IF_Adc.c ...
```

- HAL 的直接上层（典型为 Service）**只 `#include` `If/` 下的接口头**，永远看不到 `Impl/` 与具体芯片；存在独立
  Service 层时，App 只包含 Service 的公开头文件，不包含 HAL 头文件。
- HAL 的 `Impl/` 按目标设备选择依赖：片内外设实现调用 MCAL；外挂芯片实现调用 CDD；走 AUTOSAR 基础软件的实现调用 BSW。
  CDD/BSW 再各自调用 MCAL 的总线/存储接口。CDD 与 BSW 平级、互不 `#include`。
- **换硬件** = 换一份 `Impl/`，接口头不动，上层零改动 → 可移植。
- **测试** = 链接一份打桩的 `Impl/`（或编译期/链接期替换），即可在主机上单测上层逻辑而无需真实硬件 → 可测试。
- 接口头里用契约注释钉死语义（示例）：
  ```c
  /** @thread_safe @isr_unsafe @blocking 1ms(SPI)  返回 IF_OK / IF_ERR_PARAM / IF_ERR_TIMEOUT */
  IF_Status_t IF_Adc_Read(AdcChannelId_t ch, uint16_t *out_raw);
  ```
- 统一返回码类型（如 `IF_Status_t`：`IF_OK/IF_ERR_PARAM/IF_ERR_TIMEOUT/...`）放在横切 `Types` 里，全工程共用。

> 这套 If/Impl 是**推荐范式**，不是唯一解；若 SAD 已定义了别的抽象方式（如函数指针表 / 弱符号 / 配置宏切换），
> 按 SAD 来，但仍要保住"上层不依赖具体实现、实现可替换可打桩"这个本质。

## 4. 模块间与层间通信：Bus / 回调 / 接口怎么选

这一节决定模块之间、层之间**用什么机制传消息**。核心前提：**机制由产品的具体场景决定，不是定死必须用某一种。**
总线（SignalBus/EventBus）是 `cross_cutting` 里的**可选**层——很多中小项目用"调下层接口 + 回调通知上层"就够，
根本不需要 Bus。**以 SAD / 产品场景为准。**

### 4.1 先分清两个"方向"——这是不踩矛盾的关键
- **依赖方向**：谁 `#include` 谁、谁直接调谁（编译期）。分层规则（不向上、不跨层，见 §2）约束的就是它。
- **信息流方向**：消息实际从哪流到哪（运行期）。**它可以和依赖方向相反。**

横切层 / 回调的价值，正是把这两者解耦：**信息能自下而上流（下层通知上层），而代码依赖始终不向上**。
所以"下层 ISR 经 EventBus 把事件送到 App"不是跨层违规——Hal 依赖 Bus(横切)、App 依赖 Bus(横切)，
Hal 与 App 之间**没有任何编译依赖**；信息上行了，依赖没上行。回调注册同理（下层定义函数指针+注册口、上层注册，
下层调用时不知道是谁）。

### 4.2 四类通信，分别用什么
| 方向 | 机制 | 说明 |
|---|---|---|
| **上 → 下**（命令/调用） | **直接调下层接口** `IF_*`（向下依赖，合法） | 不需要 Bus |
| **下 → 上**（通知/事件） | **回调注册** 或 **EventBus** | 下层不能 `#include` 上层；二者都是依赖倒置，见 4.3 |
| **同层 ↔ 同层** | **SignalBus/EventBus** 或对方**公开接口** | 避免互相直接 `#include`、防循环依赖 |
| **取某个共享当前值**（任意层拉取） | **SignalBus** 或生产者 **getter** | 拉取语义，回调替代不了，见 4.4 |

### 4.3 下→上通知：回调注册 vs EventBus（按规模选）
两者**能力相同**——EventBus 本质就是"集中化、多对多、带 ISR 入队"的回调注册表。区别只是规模与一致性：
- **少量、点对点、固定**的通知 → **手写回调注册**更轻，不必上 EventBus。
  ```c
  /* 下层定义契约，不认识上层；上层注册自己的处理 */
  typedef void (*CrashCb_t)(uint8_t level);
  void IF_Crash_Register(CrashCb_t cb);     /* 下层触发时: if (s_cb) s_cb(level); */
  ```
- **事件多 / 一对多 / 跨很多模块 / 需 ISR 安全分发** → 用 **EventBus**；否则你会在各下层模块各写一套
  函数指针表+注册+遍历+`FireFromISR`+线程安全，等于把 EventBus 分散重造一遍，还不一致。
- **ISR 注意**：回调若直接在 ISR 上下文里调上层代码，上层逻辑就被塞进了中断（不能阻塞、要加锁、拖累时序）。
  EventBus 的 `FireFromISR` 统一做"ISR 只入队、任务上下文再分发"，把上层逻辑挪出中断。手写回调要自己处理这点。

### 4.4 共享当前值：SignalBus vs getter（按消费者数与节奏选）
"频繁读电流/电压"这类是**拉取**（消费者在自己周期醒来时要那一刻的最新值），不是推送，回调并不适配。可选：
- **生产者 getter，消费者直接调**：会引入**消费者→生产者的直接依赖**（同层硬耦合；若向上读则违规）。
  消费者少、关系固定时可接受。
- **SignalBus（按 ID 读数据池）**：消费者只依赖 Bus、不认识生产者 → **共享状态的同时解耦**。
  ```c
  /* 生产者写一处 */ SignalBus_Write(SIG_VBAT, &v, sizeof(v));
  /* 各消费者按自己节奏读，不必各存缓存 */ SignalBus_Read(SIG_VBAT, &v, sizeof(v));
  ```
- **"用推送回调替代拉取"会退化**：若让生产者每次更新就回调推给所有消费者，结果是**每个消费者各存一份"最近值"
  缓存**、回调跑在生产者任务里、还要跨任务加锁——一份共享值被拆成 N 份副本，等于手搓一个分散版 SignalBus。

### 4.5 选择判据（写进代码前据此决定，记录到 SAD/设计说明）
- 频繁读取分两种：**单消费者 + 采算同步**（如电机电流环 FOC，采一次算一次）→ **推送/回调/在采样任务里直接算**，
  最简单，不需要 SignalBus；**多消费者 + 各自周期 + 只要当前值**（电压/SOC/温度喂多个监控）→ **SignalBus**。
- 通知：点对点少量 → 回调；多对多/ISR 密集 → EventBus。
- 评估"要不要 Bus"就问两条：① 有没有"事件多/一对多"的通知（没有→不要 EventBus）；② 有没有"一份状态多模块读、
  又不想互相依赖"（没有→不要 SignalBus）。两条都没有 → **整个 Bus 都不要**，调接口 + 回调即可，完全合规。
- 现实常**两者并用**：硬实时单环走推送/回调，多消费者状态走 SignalBus。
- 决定写进 `layers.json`：用 Bus 就在 `cross_cutting` 里声明它（架构图会自动画成竖条跨使用者层）；不用就不声明。

> 数据传递的 MISRA 向细节（优先参数/返回值、禁裸 `extern` 全局、复杂数据 `const T*` 传指针）见 §6，与本节配套。

## 5. 目录布局与命名（模块化结构）

- **目录即分层**：顶层目录一眼能看出层（如 `Source/App`、`Source/Service`、`Source/Hal/If`、`Source/Hal/Impl`、
  `Source/Cdd`、`Source/Mcal`、`Source/Os`）。
- **每层、每模块各有独立文件夹**（默认）：每层一个层目录，层目录下**每个模块再独立一个子目录**，模块的
  `<前缀><Module>.h/.c/_Cfg.h` 收在自己的文件夹里。`scaffold_tree.py` 默认就这么建（`<层基目录>/<模块>/`）；
  只有在确有理由（如该层模块极少）时才用 `module_spec` 的 `"flat": true` 退化为同层平铺，且应是例外而非常态。
  *为什么*：一模块一文件夹让职责边界、依赖、测试桩、README 都就近聚拢，新增/删除模块不影响别人，维护时一眼定位。
- **文件名加层前缀**：每层用统一前缀，文件名一看就知道属于哪层、是不是对外接口。前缀在 `layers.json` 的
  `file_prefix` 里按层声明（如 `{"Hal":"IF_","App":"App_","Service":"Svc_","Cdd":"Cdd_"}`），`scaffold_tree.py`
  自动给文件名/文件夹/头文件保护/默认符号加上（模块名已带前缀则不重复加）。前缀取值以**项目现状/SAD/`NameRules.txt`
  为准**，示例里的 `IF_/App_/Svc_` 只是示意。
- **命名其余约定**：遵循项目既有 `NameRules.txt`（若有）——缩写全大写、完整单词首字母大写、`_` 作分隔、
  文件名英文无空格。不要套用任何示例项目的具体名字。
- 每个模块/层目录放一个简短 `README`（可选）说明职责与对外接口，方便维护者快速定位。

## 6. 层间数据传递与全局变量（接口契约的一部分）

目标：层与层、模块与模块之间的数据流**显式、可追踪、可测试**，而不是靠一堆裸全局变量隐式耦合。

- **优先用函数参数和返回值传数据。** 一次调用要的输入走参数、产出走返回值或出参，这样数据流写在接口签名里，
  读代码/写单测/打桩都清楚。*为什么*：参数/返回值让函数自包含、可独立测试；隐式读写全局会让行为依赖看不见的状态，
  难测难复现。
- **禁止裸 `extern` 全局变量做跨模块共享。** 跨文件的可写全局是耦合与并发隐患的温床（也踩 MISRA 8.x）。
  确需暴露状态时，暴露**访问函数**（getter/setter）而非变量本身，把表示与并发保护藏在实现里。
- **模块内部状态用文件作用域 `static`**，不对外可见；需要对外的才经接口给出。
- **复杂/成组数据用结构体，按指针传递**：入参只读用 `const T *`（不拷大对象、不可改），出参用 `T *`；
  调用方拥有内存（无动态分配），被调方不持有越生命周期的指针。在头文件里把这些公共结构体 `typedef` 定义清楚
  （见 `module-templates.md`：公共数据结构属于 `.h` 契约）。
- **"避免滥用全局"≠"禁止共享状态"，而是共享必须经受控接口**：跨模块共享状态走 `SignalBus`、访问函数(getter)
  或回调，而不是裸 `extern` 全局——这些都是"受控访问取代裸全局"，双方解耦、数据流仍显式、测试可喂假值。
  判据：一次调用链内的输入输出 → 参数/返回值；跨模块/跨周期/多消费者的状态或通知 → 受控接口。
  具体该选 SignalBus / 回调 / getter / EventBus，**按产品场景定，见 §4**。任何地方都不该出现裸 `extern int g_xxx;`
  被到处直接读写。

## 7. check_layering.py 的工作方式（便于理解判定）
1. 读 `layers.json`：`layers`（从高到低的显示顺序）、`peer_groups`（处于同一架构高度但默认互不依赖的层组）、
   `cross_cutting`（横切层名）、`path_map`（路径前缀→层名）、
   `architecture_edges`（SAD 定义的合法结构边，如默认的 `["Hal","Mcal"]`）、`allow_edges`（显式批准的架构偏离，
   如 `["App","Os"]`）、`strict_adjacent`（true=禁止未声明的跳层，默认 true）。
2. 解析每个 `.c/.h` 的 `#include`，按 `path_map` 给文件与被包含头各自定层。
3. 将同一 `peer_groups` 的成员映射到相同架构高度后判定：目标更高 → 向上依赖（错）；同高度但属于不同平级层且
   未声明结构边 → 平级依赖（错）；`strict_adjacent` 下目标低超过一级且不在 `architecture_edges`/`allow_edges`/
   `cross_cutting` → 跳层（错）；结构边、批准偏离和横切层放行；同一层内部 include 放行（语义解耦靠评审）。
4. 输出每条违规的 `文件 → 被包含头（当前层→目标层，原因）`，并以非零退出码让门禁失败。

## 8. 跨项目移植/复用（reusable vs project-specific）

目标：让 HAL/Service/App 各层模块在「新项目有同样需求」时能从旧项目直接移植，而不是每次重写。手法是**显式分类 + 对可复用模块加护栏 + 一条机检门禁**。

### 8.1 分类与标注
- 在 `module_spec` 给每个模块加 `reuse`：`reusable` | `project-specific`。缺省按层默认：**App → project-specific，其它层 → reusable**。
- 各层典型：
  - **HAL**：`If/` 接口头是 reusable（硬件无关）；`Impl/` 与 `*_Cfg.h` 是 project-specific（板级/SDK 绑定）。
  - **Service**：算法核（FOC/PID/滤波）、通用协议栈、诊断/参数框架 → reusable；绑定本项目业务语义的 Native/Device Service → project-specific。
  - **CDD / BSW（两条驱动栈）**：芯片协议驱动核（CDD）、AUTOSAR 协议栈核（BSW 的 CanIf/Com/Dcm/NvM 等）→ reusable；各自的板级/网络配置（`*_Cfg.h`、AUTOSAR `*_PBcfg`/`.arxml` 生成产物）→ project-specific，与 HAL 的 `Impl/` 同理。
  - **App**：顶层编排/主状态机/任务调度强制 project-specific（它就是把 reusable 部件组装成本项目的地方）；可复用的业务子功能（通用故障管理、参数管理、按键/LED 行为库等）单独切模块后可标 reusable。

### 8.2 reusable 模块四条护栏
1. **反向依赖禁止（机检硬挡）**：reusable 模块**不得 `#include` 任何 project-specific 模块**的头。与「不向上依赖」同构——一旦反向依赖，模块就被钉死在本项目，无法移植。`check_layering.py --modules <module_spec.json>` 据此判 `REUSE` 违规并门禁失败。
2. **横切依赖收敛为自包含契约**：reusable 用到的横切语义（信号/事件 ID、Cfg 默认、返回码扩展）收进自己文件夹的 `<Module>_contract.h`，不直接引用项目全局专属 ID；共用只准依赖**稳定横切**（`IF_Types` 稳定返回码、`Bus` 注册 API 本身）。→ 整个文件夹可搬走编译。
3. **可选注入**：配置量大或需运行期替换的 reusable 模块，把横切依赖在 `<Module>_Init(const <Module>Cfg_t* cfg, ...)` 注入，模块内零项目全局引用。
4. **移植参考说明**：每个 reusable 模块文件夹带 `<Module>_port.md`（scaffold 自动生成、预填已知信息，**不机检、不硬挡**，纯给移植者当接驳点清单）。

### 8.3 组装方向
- **project-specific 可以依赖 reusable（合法）；reusable 依赖 project-specific（门禁失败）。** 这正是「App 顶层编排调用 reusable 子功能」的合法路径。

### 8.4 机检边界（诚实划线）
- **硬挡**：reusable `#include` project-specific（`REUSE` 违规，非零退出）。
- **自动生成、不挡**：`<Module>_contract.h` 占位、`<Module>_port.md`。
- **靠 conformance 人工核**：port.md 接驳点是否填全填对、追溯 ID 的新项目重映射、自包含程度是否足够。
