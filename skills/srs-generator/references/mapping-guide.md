# 映射指南：系统功能 → 软件组件(SWC)，Req ID 与追溯

系统需求文档按"系统功能"组织，SRS 模板第 4 章按"软件组件 SWC"组织。这一步是把前者拆成后者。
下表是**本项目（多功能制氧机）的建议映射**——是起点不是教条；遇到实际架构文档以其为准。

## 系统功能 → SWC 建议映射

| 系统功能（SR-ID） | 建议 SWC 模块 | 模块缩写 | 主要软件需求方向 |
|---|---|---|---|
| 制氧功能 (SR-01-001) | 氧浓度闭环控制 + 压缩机驱动 | O2 / CMP | 4 座独立开关、流量 1~8L/min 调节、浓度闭环≥90%、BLDC/FOC 压缩机控制 |
| 负氧离子 (SR-01-002) | 负离子控制 | ANION | 启停、浓度输出、臭氧控制 |
| 香氛 / 香氛预留 (SR-01-003/004) | 香氛控制 | AROMA | 电源控制；（预留）香型/浓度/香棒识别 |
| 物理按键 (SR-01-005) | 按键输入管理 | SWT | 三功能独立开关消抖、长短按 |
| App 控制&显示 (SR-01-006) | 蓝牙通信 + HMI 状态 | BLE / HMI | 4 座控制、流量/浓度/香型调节、状态上报 |
| 安全保护 (SR-01-008) | 安全保护 | SAFETY | 氧浓度≥23.5% 停机报警（预留）、超温保护 |
| 电源管理 (SR-01-009) | 电源管理 | PWR | 休眠唤醒、掉电记忆、CANFD 唤醒、电源状态机 |
| 故障诊断 (SR-01-010) | 诊断 | DIAG | 压缩机异常、传感器故障、通信异常、DTC |
| 标定 (SR-01-011) | 标定 | CAL | 流量校正、浓度保证（预留）|
| 切换外置涡旋压缩机气源 (SR-01-012) | 气源切换 | GAS | 活塞压缩机停机 + 排氮电磁阀控制 |
| （基础平台，所有功能共用） | MCU 管理 / 输入采集 / 输出驱动 / 通信 | MCU/IN/OUT/COM | ADC 采样、IO 驱动、CAN/UART 收发、时基 |

模板第 4 章建议组织顺序：先 **MCU 管理**（基础），再 **输入管理**（采集类 SWC：按键、传感器 ADC），
再 **输出管理**（驱动类：背光、电磁阀、压缩机 PWM），再各**应用功能 SWC**（O2/PWR/DIAG/SAFETY/BLE…）。

## Req ID 命名
- 默认：`HOD_SRS_<MODULE>_NNN`，沿用模板前缀 `HOD_SRS_`，`<MODULE>` 取上表缩写，`NNN` 三位从 001 起。
  例：`HOD_SRS_O2_001`、`HOD_SRS_PWR_003`、`HOD_SRS_DIAG_007`。
- 若用户要项目专属前缀（如 `OXY_SRS_…`），全局替换即可，但**前缀风格要全篇一致**。

## 追溯（关键）
- 每条软件需求的 **覆盖需求 Covered Req** 字段，回链它派生自哪条系统需求 `SR-xx-xxx`（必要时加产品需求
  `FR-xx-xxx` / `DIAG-xx-xxx` / `REL-xx-xxx`）。这保证"系统需求→软件需求"双向可追溯，是 ASPICE 的核心要求。
- 一条系统需求可拆成多条软件需求；多条软件需求可共指一条系统需求。拆分时不要丢需求——
  系统需求文档里出现的每个 `SR-xx-xxx`，在 SRS 里都应至少被某条软件需求覆盖到。生成后自检一遍覆盖完整性。

### 覆盖自检必须逐条全列（不能笼统）
生成结尾的"系统需求覆盖自检表"要**把源文档每一个 `SR-xx-xxx` 逐条列出**，不要写"SR-07-001~019 已搬运"这种笼统行——那会把漏项盖住。做法：
1. 先用脚本把源 docx 里所有 `SR-` 编号抽出来（`grep -oE 'SR-[0-9]{2}-[0-9]{3}'` 或 python 正则），得到完整清单。
2. 每条标状态：✅已覆盖 / 🟡部分（含预留待释放）/ 🔩**软件不适用**。
3. **机械/结构/材料/硬件域**的需求（系统文档常标 `Assign:Mechanism`，如尺寸/重量/材料/运输防护）**不要硬塞进软件需求**，而是单列一节（如"§5.x 物理/机械需求（软件不适用）"）并在自检表标 🔩——既不漏、也不越界。
4. 生成后再跑一次脚本核对：源文档每个 SR-ID 是否都在 SRS 文本中出现；列出差集，确保为空。这样给出的"覆盖率"才是真实的。
- 内容其实已写、只是没引 ID 的，补上"覆盖需求"里的 ID 即可，不必为追溯重复造需求。

## 描述句式与可量化
- 描述用"The <模块> shall …"对应中文"<模块>应…"句式，写**可验证**的行为，避免含糊。
- 能量化就量化（周期、阈值、量程），数值来自系统需求/HSI/外设参数；**取不到的数值写
  `【TBD-待补充：<需要什么>】`，绝不臆造**（尤其 ASIL、时序、内存预算）。

## TBD 文案约定
统一格式：`【TBD-待补充：<具体缺什么 / 需要哪份输入>】`，例如：
- `【TBD-待补充：氧浓度传感器量程与精度，需外设参数表】`
- `【TBD-待 HARA：本需求 ASIL 等级】`
- `【TBD-待补充：压缩机转速环周期，需控制策略文档】`
便于事后全局搜 `【TBD` 定位所有待办；评审时一目了然。

## 预留功能处理
系统需求里标"（预留）"的（香氛预留、标定、部分安全/网络安全）：在 SRS 中**保留章节占位**，写明
"该功能系统需求标记为预留，软件需求待系统需求释放后补充"，并标 TBD——既不漏项，也不编内容。
