# SAD 模板结构参考（AU-QR-R&D-032 V2.1）

模板是中英双语 ASPICE 风格软件架构设计规格说明书。本 skill 只借它的**结构**，内容统一中文。模板里的
`<子系统名 #1>`、`e.g. APP`、`<服务名>` 等是**占位/示例**，生成时按本项目实际替换，不要照抄。模板原文件是
旧版二进制 `.doc`——读骨架/做最终 docx 前先 `soffice --headless --convert-to docx` 转一次。

## 关键表字段 schema

### 组件定义表（7.2.3，每个组件一行或一块）
`组件ID | 组件名/实现模块 | 所属子系统/层 | 职责描述 | 对外提供的服务/接口 | 依赖 | 实现需求 | ASIL`
- **依赖** 列写的是**编译期依赖**，且每一条都必须落在 7.2.1 合法结构边表里的某条边上，
  或指向横切层。这一列与 7.2.1 的图、第 8 章的「外部接口(依赖)」行构成同一份依赖关系的三处表述，
  `scripts/layer_check.py` 会交叉比对，三者必须一致且全部合法。常见写错：
  应用层组件直接依赖硬件抽象层组件（越层）、服务层组件依赖应用层组件（反向）、同层组件互相依赖（层内耦合）。
- **实现需求** 列是追溯关键，三种写法含义不同，不要混：
  - 列出需求 ID → 正常；
  - 写 `【TBD-…】` → 已知缺口，需求侧待补齐（`trace_check.py --reverse` 会 warn）；
  - 写「（服务于 X）」等散文理由 → 使能型组件不直接实现需求，但存在理由已说明；
  - **留空或写 `—`** → 来历不明的组件，反向追溯断裂，会被判为 fail。
- **组件名/实现模块** 列建议用反引号标出真实模块/目录名（如 `` `APP_O2` ``）：
  `trace_check.py --code-root` 靠它把文档组件与代码目录对上，才能报架构漂移。
- ASIL 列按项目的功能安全范围决定；本期不涉及功能安全的项目统一填 `NA（本期不涉及功能安全）`。

### 组件 API / 服务表（8.x.y 组件 API → 服务）
每个服务一块：`服务名 | 原型/签名 | 方向(同步/异步,调用/被调用) | 入参 | 出参/返回 | 描述 | 关联信号/需求`
- Demo 阶段签名未定时给建议原型并标 `【TBD-待软件详细设计 SWDD 细化】`（详细设计是下游 swdd-generator 的事）。

### 进程/任务表（5.1）
`任务名 | 触发(周期/事件) | 周期(ms) | 优先级 | 承载组件 | 职责`
- 周期来源：SRS 5.2 实时约束（响应≤200ms、故障检测 200ms、休眠超时 5s…）；缺的标 TBD。

### 内存映射表（7.3）
`区域 | 起止地址 | 大小 | 用途 | 备注`——多为 `【TBD-待补充：需 MCU 数据手册/链接脚本/资源预算】`。

### 软件外部接口表（3.5）——**对照 HSI 逐一列全，别照搬 SRS**
按接口类别分组列表（每组一张小表）：**① 总线/通信**（CAN0/CAN1/LIN/UART/SPI…）**② 模拟输入 ADC**
**③ 数字输入 DI** **④ 数字/PWM 输出 DO** **⑤ 看门狗/复位**。每行带真实 **MCU 网络端口名**（取自 HSI PINMUX）：
`接口/信号 | MCU 网络端口 | 类型 | 方向 | 描述 | 关联信号/报文`。
- 数据源：`HSI/*端口定义*.xlsx`（连接器→信号）+ `HSI/*管脚定义*PINMUX*.xlsx`（网络端口名）；**不要只搬 SRS 3.6**
  （常是节选且可能有错）。与 SRS 冲突以 HSI 为准，并在表后注"与 HSI 核对的更正"。
- **易错点的类别**（按这几类逐项核对，比记具体条目管用）：
  ① **总线归属误记**——某传感器实际挂在独立的内部总线上，需求文档却写成模拟采样；
  ② **引脚以 PINMUX 实配为准**——需求里的引脚可能是未启用的备选功能脚；
  ③ **执行器类型误记**——步进电机被写成 PWM 占空比驱动，或反之；
  ④ **通道数/采样点遗漏**——多相驱动的相电流、母线电流等采样通道在需求里被略去。
  *（示例：某车载项目实测到的四条恰好各属一类——PM2.5 走独立内部 CAN 而非 ADC；主 CAN 引脚以 PINMUX 为准；
  流量阀是步进电机不是 PWM；压缩机是 6 路 BLDC/FOC PWM + 相/母线电流采样。）*

### 通信机制表（7.2.5）——同层协作与下→上通知走什么
`方向 | 机制 | 适用场景 | 本项目选择`

必须覆盖四类方向，每类明确选一种机制并写清理由：

| 方向 | 可选机制 | 判据 |
|---|---|---|
| 上→下（命令/调用） | 直接调下层接口 | 向下依赖，合法，不需要总线 |
| 下→上（通知/事件） | 回调注册 / 事件总线 | 点对点少量→回调；多对多或 ISR 密集→事件总线 |
| 同层↔同层 | 信号总线 / 事件总线 / 对方公开接口 | 避免互相 include 导致模块环；有环必须用总线拆开 |
| 取共享当前值 | 信号总线 / 生产者 getter | 多消费者各自周期取值→总线；单消费者且关系固定→getter 可接受 |

**为什么这一节非有不可**：不写，同层能不能互调就没有裁决，代码里会长出模块环，而评审时拿 SAD 判不出对错。
另外要在此写明**信息流方向可以与依赖方向相反**——下层经回调/总线把事件送上去，信息上行而编译依赖不上行，
这不是反向调用。第 9 章的时序图箭头是信息流，读图时按这条口径理解。

> 项目若既没有"一对多事件通知"也没有"一份状态多模块读"，就不要引入总线，调接口 + 回调即可，
> 此时在本节写明"不设总线"并说明理由，同样是合格的架构决策。

### 状态机表（5.3 运行模式 / 5.4 功能模式）——每个状态机配两张表
**状态说明表**：`内部状态编号 | 对外上报 | 状态 | 用途/职责 | 关键活动`
（5.4 功能机可按功能分组：`功能机 | 状态 | 说明 | 关键活动/信号`）。
**状态转移条件表**：`序号 | 起始状态 | 跳转状态 | 跳转条件`——序号 C1/C2…（全局机）或 F1/F2…（功能机），
与状态机图连线序号一一对应；条件保留 `&&`/`||`/`!`、`//` 后回链需求 ID（表格内 `|` 写 `\|`）。详见 `diagram-guide.md ②`。

### 追溯矩阵（文末，**逐条全列每个需求 ID**）
| 需求 ID | 标题 | 实现组件ID | 相关时序/状态机 | SAD 章节 | 状态 |
|---|---|---|---|---|---|
| `<PREFIX>_SRS_XXX_001` | <需求标题> | C-AAA、C-BBB | 9.4 <功能>时序 | 7.2.3、8.1.1 | ✅ |
| `<PREFIX>_SRS_YYY_001` | <需求标题> | C-CCC | 5.3 <名称>状态机、9.2 <名称>时序 | 5.3、9.2 | ✅ |

**「实现组件ID」列必须写组件ID，不要只写章节号**。组件ID 是稳定标识，章节号会随文档增删组件而漂移；
两列并存时以组件ID 为准、章节号仅作导航。文档迭代时组件小节编号**冻结不动**（见上文第 8 章说明），
新组件追加编号，这样矩阵才不会在一次重新生成后集体失效。

状态：✅已覆盖 / 🟡部分（含预留待释放，如标定 CAL、高氧停机）/ 🔩硬件域（软件不适用）。
**做法**：先用 `grep -oE '[A-Z0-9]+_SRS_[A-Z0-9]+_[0-9]+' <srs.md> | sort -u` 拿全量需求清单，逐条列；生成后用
`scripts/trace_check.py` 核验未覆盖集为空。覆盖率要真实——不能写"O2_001~007 已覆盖"这种笼统行盖住漏项。
