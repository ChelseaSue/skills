# SAD 输入缺口清单（各章节需要什么 / 缺了怎么提示）

第 2 步"缺口提示"用这张表。对每项判断：**已找到**（来自哪个文件）/ **部分**（有但不全，说明缺的维度）/
**缺失**（请用户补充，或说明将用 TBD 兜底）。给用户的提示要具体——说缺哪一项、影响 SAD 哪个章节、能否 TBD。

约定：
- **能 TBD 兜底** = 缺失不阻断起草，先写 `【TBD-待补充：…】`，不影响其余章节。
- **建议先补** = 缺了会让大段内容变空壳或编造（如组件 API、内存预算），强烈建议先给，否则明确告知该章多为占位。
- SAD 的特点：**主输入 SRS 通常齐全**（架构、组件、时序、信号的素材都在 SRS 里），缺口几乎全集中在
  **"设计决策"**——这些 SRS 不负责给，往往项目里也还没文件。这正是要在第 2 步向用户点名的部分。
