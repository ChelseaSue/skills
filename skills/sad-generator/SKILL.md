# SAD 生成器（软件需求 SRS → 软件架构设计 SAD）

把按"软件组件(SWC)需求"组织的 SRS，转成一份**软件架构设计规格说明书**：分层架构、组件分解与接口、
实时/内存/鲁棒性设计、各功能的动态时序，并保证**每条软件需求都在架构中有去向**。

文档链：系统需求 →（`srs-generator`）→ **SRS** →（**本 skill**）→ **SAD** →（`swdd-generator`）→ SWDD。

这不是格式转换：SRS 说"软件要做什么"，SAD 说"软件怎样搭起来去满足这些需求"。模板里大量内容（RTOS/调度选择、
CPU 负载、内存映射、NVM 设计、中断/任务划分、看门狗、组件 API、部署视图……）是**设计决策**，SRS 里没有。
所以**先盘点缺什么，再起草，缺的地方明确标 TBD**，并把判断权交还用户。

## 通用性（务必保持——本 skill 适用于任意嵌入式项目，不绑定任何单一项目）
层数、层名、组件名、需求 ID 前缀、功能清单、输出路径**一律来自输入文档**，不得把某个项目的取值写进
流程正文。参考资料里出现的具体功能名/信号名/引脚都标注为**示例**，照抄进产出即为缺陷。
项目级的范围决定（是否涉及功能安全、通信矩阵是否就绪、哪些功能预留）属于**每项目的决策记录**，
在第 2 步向用户确认后记在缺口清单顶部，不写死在本文件里。

## 何时用、产出什么
- 输入：一份 SRS（优先 Markdown，其次 docx，**主输入**）+ 软件架构模板（.doc/.docx）+
  通信矩阵（CAN/LIN，供时序图标注真实信号）+ **已有代码根（若项目已有代码，见第 3.5 步架构对账）**
  + 同项目其它文档（本 skill 自动发现）。
- 中间产物：**中文 Markdown 版 SAD**，所有图以 **PlantUML 源码**内嵌（```plantuml``` 代码块）。
- 最终产物（按需）：把 PlantUML 图渲染成 PNG、克隆模板 docx 填充后的 `.docx`。
- 语言：**统一中文**。模板原文是中英双语，只借它的结构，不照抄英文。

## 四条硬性要求（务必满足）
1. **调用即先做缺口提示**（见第 2 步）——动手生成前先点出"SRS 之外还缺什么"。
2. **双向可追溯**——正向：每条软件需求都要在 SAD 里落到某个组件/时序/章节；反向：每个组件都要说明它
   实现哪条需求，或写明存在理由/TBD。结尾给全量追溯矩阵，用 `trace_check.py --reverse` 核验：
   未覆盖集为空，且没有来历不明的组件。
3. **分层自洽且可机器校验**——分层规则（单向、不越层、层内隔离、平级隔离、横切任意可用）必须在 7.2.1
   写成**规则表 + 合法结构边表**；7.2.3 组件表的依赖列、第 8 章各组件的依赖行必须与之一致。
   用 `layer_check.py` 核验：违规为 0、三处表述一致。
4. **三类必含图**——① 软件分层架构图（→7.2.1）② 软件状态机图（→5.3/5.4）③ 各功能动态
   时序图，**标注实际使用的通信信号名+报文ID+收发方向**（→第 9 章）。

## 工作流（6 步，按顺序做，第 2 步不可跳过）

### 1. 定位输入
确认 SRS（优先 `.md`）、软件架构模板、通信矩阵、**已有代码根**的路径。运行发现脚本扫描同项目补充文档：
```bash
python3 scripts/discover_inputs.py <项目根目录>
```
它按目录/文件名分类（SRS/架构模板/通信矩阵/**已有代码根**/系统需求/产品需求/HSI/外设/硬件架构…），
输出"已找到 vs 缺失"，并列出**通常无文件可扫的"设计决策类"输入**供第 2 步点名。
若用户只给一个文件没给项目根，以该文件目录的上一级当根。
**扫到代码根就意味着这是棕地项目**，第 4.5 步的架构对账必做——否则文档与代码必然从第一版就开始漂移。

### 2. 缺口提示（调用时必做——这是用户的硬性要求）
**在动手生成之前**，先给用户一张"SAD 所需输入 vs 已找到 vs 缺失"清单，明确点出**SRS 之外还缺什么**，
请用户补充、或确认"以 TBD 占位继续"。为什么必须先做：SAD 模板要求 RTOS/调度选择、CPU 负载预算、内存映射、
NVM 数据字典、中断/任务划分、看门狗策略、组件 API 契约、部署视图等——这些 SRS 里没有；闷头生成会编造或静默
漏掉。把判断权交还用户。

**尊重用户已定的范围决定**：范围决定是**每项目**的，第一次问清后记在缺口清单顶部，之后不再反复追问。
典型的几类：① 功能安全是否在本期范围内——若确认不涉及，ASIL 列统一填 `NA（本期不涉及功能安全）`，
不要满屏 `【TBD-待 HARA】`、也不要再当缺口；② 通信矩阵是否已就绪——就绪则时序图直接用真实信号；
③ 哪些功能属于预留待释放——预留项标注占位，不编内容。
这些决定连同日期一并写进缺口清单，作为本项目的决策记录。

缺口判断细节见 `references/input-checklist.md`，含给用户的提示输出范例。

### 3. 解析输入
- **SRS（主输入）**：若是 `.md`，直接读——它已是结构化中文，含每条 `<PREFIX>_SRS_*` 需求表（13 字段）、SWC 清单
  （3.7.1）、逐信号 CAN 表（3.5/3.6）、覆盖自检表。若只有 docx：`python3 scripts/extract_docx.py <srs.docx>`。
- **通信矩阵 → 信号查找表**（时序图要用）：
  ```bash
  python3 scripts/parse_can_matrix.py <通信矩阵.xlsx>            # 报文/信号/起始位/收发方向
  python3 scripts/parse_can_matrix.py <通信矩阵.xlsx> --signal <信号名片段>   # 单信号速查
  ```
  它能恢复每个报文的**收发方向**（控制帧 外部→本机、状态帧 本机→外部），据此决定时序图箭头朝向。
- **HSI 逐一核对软件外部接口（§3.5 关键，别照搬 SRS）**：读项目的端口定义表（连接器→信号）与
  管脚定义/PINMUX 表（MCU 网络端口名）。**§3.5 软件外部接口必须对照 HSI 逐一列全**——SRS 的接口章节常是
  节选且可能有错。按四类典型偏差逐项核对：① **总线归属误记**（传感器实际挂独立内部总线，却被写成模拟采样）；
  ② **引脚以 PINMUX 实配为准**（SRS 写的可能是未启用的备选功能脚）；③ **执行器类型误记**（步进电机被写成
  PWM 占空比驱动，或反之）；④ **通道数/采样点遗漏**（多相驱动的相电流、母线电流被略去）。
  **冲突时以 HSI 为准**，并在 §3.5 末尾注明"与 HSI 核对的更正"。
- **模板骨架核对**：`python3 scripts/extract_docx.py <032模板.docx> --headings`（.doc 先 `soffice --headless
  --convert-to docx` 转一次）。章节树与各表 schema 已整理在 `references/template-structure.md`。
- **复用源图**：SRS 已有的系统框图/产品外形图在其 `srs_images/` 里，可直接 `![](…)` 引用，不必重画。

### 4. 架构推导 + 建追溯底座
- **先定层模型，再归位组件**。层数与层名由项目决定，`references/diagram-guide.md ①` 给了嵌入式 MCU 常见的
  一套（应用 / 服务（含 OS 适配）/ 硬件抽象 / 复杂驱动·基础软件（平级）/ 芯片抽象·操作系统（平级）/ 横切）
  作为起点，按项目增删——没有外挂芯片就不要复杂驱动层，不用 AUTOSAR 就不要基础软件层。
  **注意两条最常画错的边：芯片抽象层与操作系统平级、互不依赖；应用层不直连硬件抽象层。**
- **把分层规则写死成表**：7.2.1 除了图，必须给**分层规则表**（单向 / 不越层 / 层内隔离 / 平级隔离 /
  横切任意可用）与**合法结构边表**。后者是 `layer_check.py` 的输入，也是导出层模型交给 `code-generator`
  的依据——只画图不给表，下游只能从散文里猜架构。
- **决定同层协作机制**（→7.2.5 通信机制）：同层模块要不要互相依赖、下→上通知走回调还是总线，
  在架构阶段就裁决并记录。不裁决的后果是代码里长出模块环，而评审时拿 SAD 判不出对错。
- **组件归位**：把 SRS 的每个 SWC 落到某一层，给每个组件定**稳定的组件 ID**，
  并在组件名列用反引号标出实现模块/目录名（供后续与代码比对）。
- **建追溯映射**：为每条需求 ID 记下"实现于哪个组件 / 体现在哪张时序图或状态机 / 落在 SAD 哪一章节"。
  这是结尾追溯矩阵的数据底座。一条需求可由多个组件/时序共同实现；不要丢需求。
- 详见 `references/template-structure.md`（追溯矩阵列定义）。

### 4.5 架构对账（项目已有代码时必做）
SAD 常常是给**已经有代码的项目**补的。只从 SRS 单向推导，推出来的是理想架构，与既存代码零对账——
文档一出生就是错的，而且错得很隐蔽（章节齐全、追溯 100%，就是和代码对不上）。

若第 1 步发现了代码根，在生成正文前先出三张对账表，请用户逐项裁决"改文档还是改代码"：

| 对账项 | 怎么查 | 典型成因 |
|---|---|---|
| 代码有、文档无 | 代码里的模块目录在组件表里找不到 | 后加的功能没回写架构 |
| 文档有、代码无 | 组件表里的组件在代码里没有对应目录 | 预留组件，或架构先行 |
| 层归属不一致 | 同一模块，文档说在 A 层、代码在 B 层目录下 | 实时算法核、板级启动这类归属易错的组件 |

```bash
python3 scripts/trace_check.py --srs <srs.md> --sad <sad.md> --reverse \
    --code-root <代码根> --code-exclude <厂商/生成目录片段,逗号分隔>
```
裁决结果写进 SAD 的架构决策记录（谁、哪天、决定采用哪一侧、理由）。
**不要自行判断"代码写错了"就按理想架构写文档**，也不要反过来把代码里的违规照抄成架构。

### 5. 生成 Markdown SAD
严格按 032 九大章结构（见 `references/template-structure.md`）输出中文 Markdown，**所有图用 PlantUML 源码**
（```plantuml``` 或 `@startuml`）。画法见 `references/diagram-guide.md`：
- **软件分层架构图**（7.2.1）：按第 4 步定下的层模型分层，各 SWC 落层、画出结构边；
  **同时给出分层规则表与合法结构边表**（缺表则 `layer_check.py` 无表可查，下游也无从接手）。
- **软件状态机图**（5.3 + 5.4）：PlantUML `state`，**两层 + 三段式**（详见 `diagram-guide.md`）。5.3 全局运行
  模式机（初始化/运行/故障降级/休眠，功能无关、统一门控；休眠判据必须"功能感知"——**所有功能空闲、无本地输入
  活动、且总线静默才休眠**，否则用户用实体按键单独开着的功能会被误关）。5.4 各功能并行模式机（项目有几个可
  独立启停的功能就几台，**不合并成组合大机**；多来源指令的优先级仲裁放指令层）。每个状态机小节都给
  **状态机图（连线仅标序号 C/F）+ 状态说明表 + 状态转移条件表 + 设计要点**。
- **各功能动态时序图**（第 9 章）：PlantUML `sequence`，**每个功能模块一张** + 模板固有的初始化/休眠/唤醒
  时序。participant 用 外部系统/通信组件/各 SWC/执行器；若项目用信号总线做同层协作与状态上行，**把总线也画成
  一个 participant**，否则「功能模块 → 聚合模块」会被读成反向调用。箭头标**真实信号**
  `<报文ID> <信号名>`，信号名/方向取自 `parse_can_matrix.py`。
  时序图的箭头是**信息流**、不是依赖——这一点在 7.2.5 通信机制里写明，读图才有统一口径。
- **追溯（双向）**：每个组件定义、每张时序图、每个架构元素都**标注它实现/覆盖的需求 ID**；结尾给**全量追溯矩阵**
  （每条需求 → 实现组件ID → 相关时序/状态机 → SAD 章节 → 状态 ✅/🟡预留/🔩硬件域），镜像 SRS 的覆盖自检表风格。
  反过来，**每个组件的「实现需求」列都不能留空**：实现了哪条就写哪条；使能型组件（门面、OS 适配、总线、
  类型/配置）写明服务对象；需求侧确实还没有的写 `【TBD-…】`并回头补 SRS。留空即视为来历不明的组件。
- 缺信息处统一写 `【TBD-待补充：<具体需要什么>】`，不要编造数值；备选方案（第 6 章）缺真实评审记录时写
  "建议方案，待软件架构评审确认"。
- **交付物口吻**：SAD 正文只写"软件架构本身"。两类东西**一律不写进正文**：① 缺口分析、gap 报告、"项目无 XX 文档"
  （只属于缺口提示）；② **文档生产过程的元信息**——用什么工具/脚本生成、图源/文件来源、为何选某格式、"可重生成/
  矢量源/MPE 可渲染/导出 docx 时如何"之类。图就放图、最多配一句对图**内容**的解读；工具与溯源信息留在配置或交付物
  之外，不进正文。
默认输出到项目的软件架构目录下 `<项目名>软件架构设计_draft.md`（或用户指定路径）。

### 6.（按需）生成最终 docx + 追溯核验
用户说"出 docx / 转成 Word / 生成最终文档"时：
```bash
# 渲染图：rendered-md 要和 --outdir 在同一目录，否则图片相对路径对不上、贴不进 docx（踩过的坑）
python3 scripts/render_diagrams.py <sad.md> --outdir 软件架构/sad_images \
    --rendered-md 软件架构/<同名>.rendered.md
python3 scripts/build_sad_docx.py 软件架构/<同名>.rendered.md --template <032模板.doc/.docx> --out <输出.docx>
soffice --headless --convert-to pdf <输出.docx>                                    # "能否打开"烟雾测试
python3 scripts/trace_check.py --srs <srs.md> --sad <sad.md> --reverse              # 必跑：双向追溯
python3 scripts/layer_check.py --sad <sad.md>                                       # 必跑：分层自洽
python3 scripts/layer_check.py --sad <sad.md> --emit-layers <layers.json>            # 交接给 code-generator
```
`build_sad_docx.py` 以模板为基底克隆，填章节、克隆表格、插入 PNG；`.doc` 模板会自动先转 `.docx`。它已内置两个
公司模板的坑修复：① 按**样式名**解析 Heading（python-docx 默认按 styleId 查会漏，导致标题退化成正文、丢目录层级）；
② **抑制 Heading 样式自带的多级自动编号**（否则与正文手写的 `4.1` 叠加成"3.1 4.1"乱号）。要修一份已有的 docx 编号，
单独跑 `python3 scripts/fix_heading_numbering.py <file.docx>`。
**两个门禁都必须跑通**（需求 ID 前缀随 SRS，脚本默认前缀无关，自动识别常见写法）：
- `trace_check.py --reverse`：未覆盖需求为 0，且无"来历不明"的组件（实现需求列留空的）。
  标了 TBD 或写了服务对象的使能型组件不算失败，但 TBD 会以 warn 列出，是真实的需求缺口，要回写 SRS。
- `layer_check.py`：违规为 0，且 7.2.1／7.2.3／第 8 章三处依赖表述一致、层名写法统一。
  项目若有**层内网关**（如 OS 适配组件被同层依赖），用 `--same-layer-allow <组件ID>` 声明为豁免。
不通过就回第 5 步改，别带病出 docx——一旦转成 Word 分发，错误架构就开始被人照着写代码了。

`--emit-layers` 导出的层模型是**给下游 `code-generator` 的交接件**（同 schema：layers / peer_groups /
cross_cutting / architecture_edges）。有了它，代码生成阶段不必再从散文里反推架构，两个 skill 的分层判定
