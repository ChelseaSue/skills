# 宿主机协议行为测试：搭建与坑

## 搭建循环

1. `host.sources` 列出协议栈与配置生成物（如 LinIf/LinTp/PduR/Com/Dcm + `*_Cfg.c/*_Lcfg.c/*_PBcfg.c` + 公共工具 `Bsw_Common.c`）。
2. `stdc.py host probe`：逐文件语法探测。缺的应用层头（如 `Bsp.h`、`ARTE.h`）在 support/ 放**替身头**，只声明栈真正用到的符号，
   并在头部注释写明“这是越层依赖”——它同时是一条架构发现。同名头冲突（BSW 与 MCAL 各有一份 `Lin_GeneralTypes.h`）时调整 include 顺序。
3. `stdc.py host gen`：生成 project.yml 与每个 host-test 检查项的骨架（未实现的骨架不参与归集；被正式测试覆盖的骨架会自动删除）。
4. 写测试 → `stdc.py run --test <文件名>` → 读链接错误 → `stdc.py host stubs` 自动生成中性桩（`std_autostubs.c`）→ 再运行。
5. 测试里用 `TEST_SOURCE_FILE("x.c")` 拉入所有参与集成的源文件（Ceedling 只按 include 的头自动链接同名源文件）。

## LIN 从节点（AUTOSAR 4.4 LinIf）

用包内 `std_lin_bus.h/.c` 扮演 LIN 驱动：`StdLin_Header(id)`（本节点发布则取回应答并确认）、`StdLin_Rx(id, data)`、
`StdLin_RxError(id, err)`、`StdLin_HeaderPid(pid)`（注入奇偶错误）。诊断请求从 0x3C 注入，应答从 0x3D 报头取回；
每次取回前推进一次各 MainFunction（按 Dcm/LinTp 周期折算节拍）。

## 坑（务必先排除，再下“不符合”结论）

| 坑 | 后果 | 处理 |
|---|---|---|
| 自动桩替换了栈依赖的真实工具函数（如 `Bsw_MemCpy`） | 数据没被拷贝，所有接收都“失败”，得出大量假“不符合” | `host stubs` 会标注“项目中存在真实定义”的符号；这类工具函数把源文件加进 `host.sources`，不要打桩 |
| 一个检查项同时被骨架和正式测试标记 | 骨架为忽略状态，检查项被判“未检查” | 骨架保持原样就不计入；`host gen` 会删除已被覆盖的骨架 |
| 测试第一次失败就记为不符合 | 可能是测试环境问题 | 先逐层注入（驱动回调 → PduR → Com/Dcm）确认数据走到哪一层；能稳定复现且排除环境原因后才判“不符合” |
| BSW 中嵌有应用逻辑（如 LinIf 按应用状态过滤某帧） | 测试结果受边界桩返回值影响 | 在边界桩里显式设置该应用状态，并把这种耦合记入报告的发现项 |
| 用宿主机时间判定 | 结果不可复现 | 一律按 MainFunction 调用次数（节拍）判定 |
| 同一测试程序内状态泄漏 | AUTOSAR 模块有初始化保护（如 `LinTp_Init`、`Com_Init` 二次调用直接返回），上一个测试的挂起状态带入下一个测试，出现崩溃或假结果 | `setUp` 先调用 `LinTp_Shutdown()`、`Com_DeInit()` 等反初始化，再初始化 |
| 一个测试崩溃，整个文件全部报“crashed” | Ceedling 一次运行一个可执行文件，崩溃后其余测试都无结果 | 归集时“crashed”记为未检查（不是不符合）；用 `gdb -batch -ex run -ex bt <exe>` 找到真正崩溃的测试 |
| 辅助 .c 放在 Ceedling `:support:` 路径 | 被链接进每一个测试，骨架测试链接失败，整次构建中止 | 生成器已把 support/ 作为普通源码路径，测试用 `TEST_SOURCE_FILE` 显式引用 |
| 被测功能实际在应用层（如总线静默休眠计时、进入休眠的决策） | 只测 BSW 会得出错误结论 | 测试标 `TEST_IGNORE_MESSAGE` 写明原因，改由设计评审判定，并把“功能在应用层”记为发现 |
| 协议功能不在预期的模块（如 LIN 节点配置 0xB0~0xB8 没在 LinIf 实现，而是作为 Dcm 的一个 UDS 服务） | 测试打到错误的层，或误以为“服务不存在” | 写测试前先在全部源码和配置中搜 SID/关键常量，找到真正的处理函数，读清它的请求格式和长度判定 |
| 实现只接受私有格式（如 0xB2 只收 2 字节、只认用户自定义标识符） | 标准格式请求全被 NRC 拒绝，容易被当成“测试写错了” | 对照测试同时发“实现自身格式”和“标准格式”：前者有应答即证明通路正常，后者被拒才是不符合 |
| 同名源文件/配置有多份且内容不同（配置工具新生成的一份 vs IDE 工程实际编译的手改版） | 测了不会被编译的那份，结论无效 | `host probe` 会列出 `[drift]`（已忽略注释和空白）；到 IDE 工程（.ewp/.uvprojx/Makefile）确认实际编译的路径，`host.sources` 用同一份；漂移本身记为配置管理发现（重新生成会丢失手工修改）。MCAL 中只含 `weak` 缺省实现的同名文件标为 `[weak]`，属正常 |
| 替身返回值的语义与被测模块的解读不一致（如 Dcm 把尝试计数器当“剩余次数”，替身却从 0 起算“失败次数”） | 栈进入锁定/延时等异常状态，得出假 NRC（如 0x37） | 写替身前读被测模块如何使用该值；替身初值取产品实际默认值（如应用层 EEPROM 默认 3）。出现意外 NRC 时先查替身，再怀疑产品 |
| 测试需要链接真实的 RTE/胶合层，但共享的 `std_autostubs.c` 已经把它们打成桩 | 重复定义，链接失败（MinGW 不支持可靠的弱符号覆盖） | 单独运行该测试后 `host stubs --stubs-out std_autostubs_<名>.c` 生成专属桩文件，测试改用它；原型只以 `extern` 写在 .c 里时生成器也能找到 |
| 只读代码就下“不符合”/写发现项 | 结构体字段错位、宏语义误读，结论错误 | 发现项与 notes 中的配置结论要对照类型定义逐字段核实；能用测试验证的先跑测试 |
| 节拍函数里 MainFunction 的顺序/周期与目标机不同 | “下一个时隙内应答”“P2 内发 0x78”这类按节拍判定的结论偏差一拍 | 从目标机任务代码（OS 任务入口、BSW 周期任务）抄调用顺序与周期，在节拍函数注释里写明出处 |
